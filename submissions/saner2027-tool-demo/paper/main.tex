\begin{abstract}
Software agents now edit files, run tests, inspect repositories, and prepare
changes that may affect downstream maintenance. This tool demonstration
presents a replayable harness for evaluating whether such agents operate under
explicit state and permission contracts. The artifact models tool calls,
observations, permission gates, memory scope, replay, and final state diffs. It
contains 24 cases, raw run logs, regenerated tables, and validation scripts. For
software analysis and evolution, the key contribution is an inspectable way to
treat an agent trajectory as a maintainable software artifact: what changed,
which tool produced it, whether policy allowed it, and whether the failure can
be replayed. Tool: \url{https://github.com/rrrrrredy/agent-harness-paper}.
Archive: \url{https://doi.org/10.5281/zenodo.20907471}. Video:
\url{https://github.com/rrrrrredy/agent-harness-paper/releases/download/v0.1.0-preprint/agent-harness-saner-tool-demo-video.mp4}.
\end{abstract}

\section{Problem}

Coding and workflow agents create new maintenance questions. A final answer
does not reveal whether the agent edited the intended file, respected a dry-run
policy, avoided secrets, scoped memory correctly, or left a replayable trace.
These questions are central to software analysis, evolution, and
reengineering because agent behavior becomes part of the evolving development
process.

The problem is not limited to wrong answers. A repository-changing agent can
produce a plausible summary while skipping tests, touching an unrelated file,
using stale memory, accepting an injected instruction from an observation, or
preparing an irreversible side effect without review. These are software
analysis problems because the evidence is distributed across files, commands,
tool calls, policy decisions, and final state.

\section{Tool}

The demonstrated tool is a small replayable harness for stateful agent
contracts. It provides:

\begin{itemize}
\item case definitions with initial state, allowed tools, forbidden tools, and
state assertions;
\item mock tools for file, repository, memory, email/browser-like, and review
state;
\item prompt variants for no harness, thick checklist, and thin contract;
\item metrics for task success, state-diff correctness, invalid tool calls,
permission violations, unsafe secret access, and replayability;
\item scripts for validation, regeneration, source evidence audit, and secret
scanning.
\end{itemize}

\section{Architecture}

The tool has four layers. The \emph{case layer} defines task intent, initial
state, allowed tools, forbidden tools, required tools, and final-state
assertions. The \emph{execution layer} normalizes model outputs into tool
actions and applies those actions to a mock state containing files, memory,
reports, email-like side effects, browser state, and test status. The
\emph{oracle layer} checks state assertions and policy outcomes. The
\emph{analysis layer} regenerates summary tables, failure taxonomies,
uncertainty summaries, and fixture traces from raw JSONL rows.

The repository also contains a small concrete repository fixture. It maps one
stateful tool-use case to a before/after tree: \texttt{src/app.py} begins with
\texttt{VALUE = 1}, the contract trace writes \texttt{VALUE = 2}, and a
no-dependency test checks the final value. The generated output includes a
unified diff, file hashes, and a JSON trace. This fixture is intentionally
small so reviewers can inspect the full state transition.

\section{Demo}

The demo walks through a repository-changing scenario:

\begin{enumerate}
\item load a case that requires a safe repository update;
\item show the expected tool contract and forbidden actions;
\item run the harness and inspect the resulting action trace;
\item compare initial and final mock state;
\item inspect a failure where a broad prompt checklist does not enforce the
contract;
\item regenerate aggregate tables from raw runs.
\end{enumerate}

The artifact is designed for reviewers to execute without live model keys. Live
provider runs are included as raw rows; deterministic validation checks the
simulator and metrics.

The recommended reviewer path is:

\begin{enumerate}
\item run \texttt{python scripts/run\_checks.py --mode validate};
\item run \texttt{python scripts/run\_demo\_walkthrough.py};
\item run \texttt{python scripts/run\_repo\_fixture\_demo.py};
\item inspect \texttt{results/fixtures/saner\_repo\_fixture.diff};
\item inspect the failure taxonomy under \texttt{results/tables/}.
\end{enumerate}

This path exercises the tool without requiring provider credentials. Reviewers
who want to reproduce live API runs can supply provider keys, but the
submission does not depend on those keys.

\section{Relevance to SANER}

The harness treats agent trajectories as analyzable software artifacts. It can
support regression testing of agent workflows, analysis of repository side
effects, evolution of prompt and tool schemas, and reengineering of brittle
agent scripts into explicit contracts. This fits SANER's focus on extracting
useful information from software and system artifacts and using that information
for maintenance and renewal.

The tool is particularly useful for three maintenance workflows.

\textbf{Regression testing agent configurations.} When a model, prompt, or tool
schema changes, teams can rerun the same cases and compare state-diff failures,
invalid tool calls, permission violations, and replayability.

\textbf{Auditing repository side effects.} A reviewer can inspect which file
changed, which tool produced the change, which policy allowed it, and whether
the expected validation ran.

\textbf{Reengineering prompt scripts.} Existing agent workflows often rely on
long checklists. The harness helps migrate those scripts toward explicit
contracts: allowed tools, forbidden effects, state assertions, and review
gates.

\section{Limitations}

The current artifact is a pilot tool, not a large benchmark. Most cases use
mock state rather than full repositories. The concrete repository fixture is
small. The provider rows are descriptive and should not be interpreted as a
general model ranking. The demonstration value is the analysis shape: final
answers are connected to tool traces, state diffs, policy outcomes, and replay
records.
