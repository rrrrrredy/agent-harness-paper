\begin{abstract}
Repository-changing agents create a software maintenance problem: their outputs
are not only answers, but state transitions. They edit files, inspect project
state, run commands, write memory, and prepare reviewable changes. Evaluating
only the final response hides whether the correct files changed, whether tests
or validation commands ran, whether permissions were respected, and whether a
failure can be replayed. This short paper proposes \emph{state-diff contracts}
for evaluating such agents. A contract specifies task intent, allowed and
forbidden tools, permission policy, initial and final state assertions, and
replay evidence. A 24-case pilot artifact shows how invalid tool calls,
permission violations, missing state diffs, unsafe secret access, and recovery
failures can be surfaced as analyzable software artifacts. The contribution is
a software-analysis framing for maintaining agent workflows as prompts, models,
tool schemas, and repository policies evolve.
\end{abstract}

\section{Introduction}

Software engineering agents increasingly operate inside repositories rather
than beside them. They inspect files, propose patches, run tests, update
documentation, manage memory, and prepare pull requests. These actions are
state transitions. A textual answer such as ``the task is complete'' is not
enough evidence for maintenance, review, or regression testing.

The maintainable unit is the trajectory: which tool was called, with what
arguments, after which observation, under which permission policy, and with
what final state. This paper argues that repository-changing agents should be
evaluated through \emph{state-diff contracts}. The idea is deliberately modest:
do not replace the agent with a large scripted runtime; instead, make the
external effects of the agent explicit enough to analyze.

This framing leads to two research questions.

\textbf{RQ1.} What information must be recorded for a repository-changing
agent run to be reviewable as a software artifact?

\textbf{RQ2.} Which failure classes become visible when evaluation includes
tool traces, permission policy, and state diffs rather than final answers
alone?

\section{State-Diff Contracts}

A state-diff contract has five parts.

\textbf{Intent and trigger.} The contract states when the agent should act and
what task boundary it should respect. This catches over-triggering and
under-triggering.

\textbf{Tool interface.} The contract states which tools are expected, allowed,
or forbidden, and records tool arguments and observations. This turns tool use
into a reviewable software event rather than a narrative claim.

\textbf{Permission policy.} The contract separates read-only, dry-run,
review-required, and forbidden side effects. For repository workflows, this
distinguishes running tests from deleting files, preparing a patch from merging
it, and reading project files from reading secrets.

\textbf{State assertions.} The contract defines what must change and what must
not change. For repositories, assertions may include file diffs, command
results, test status, review state, generated artifacts, and absence of
unrelated changes.

\textbf{Replay evidence.} The contract preserves enough input, configuration,
tool observations, and final state to diagnose the run. Replay is essential
because failures may come from the model, prompt, tool schema, repository
state, memory, or policy.

The contract is not intended to specify how the agent reasons internally. It
specifies the boundary between the agent and the software environment. This
keeps the evaluation stable as models and prompts change. A planner may be
rewritten or removed, but a forbidden secret read remains forbidden; a required
test remains required; an expected patch remains observable as a diff.

\section{Pilot Artifact}

We implemented a small anonymous pilot artifact with 24 cases. The cases cover
trigger/routing behavior, stateful tool use, permission and prompt-injection
conditions, memory scoping and forgetting, and replay/failure recovery. Each
case defines mock initial state, allowed tools, expected tools, forbidden
tools, final-state assertions, and metrics.

The pilot includes three prompt variants. The \emph{no-harness} variant gives
the task with minimal operational structure. The \emph{thick-checklist} variant
adds broad reminders. The \emph{thin-contract} variant provides concise
boundary contracts: allowed tools, forbidden tools, state assertions, and
review expectations. Recorded runs are evaluated for task success,
state-diff correctness, invalid tool calls, permission violations, unsafe
secret access, replayability, and recovery behavior.

The pilot is intentionally small and synthetic. It is not a provider benchmark.
Its purpose is to test whether the harness surfaces maintenance-relevant
failures. It does: several failures that would be ambiguous in final answers
become concrete artifacts. A secret-read attempt is a forbidden access event. A
repository update without the expected diff is a state assertion failure. A
dry-run bypass is a permission violation. A recovery claim without a replayable
trace is a replay failure.

To make the repository-state claim concrete, the artifact also includes a small
repository fixture for case \texttt{state\_002}. The fixture starts with
\texttt{src/app.py} containing \texttt{VALUE = 1}, applies the contract trace
that writes \texttt{VALUE = 2} and runs a no-dependency test, then emits a
unified diff, file hashes, and a JSON trace. The generated fixture result has a
passing state-diff assertion, no permission violations, and a replayable action
record. This is not a large benchmark, but it demonstrates the intended
software-analysis object: the agent run is inspected as a repository diff plus
policy and test evidence.

\section{Findings}

The pilot supports three qualitative findings.

\textbf{F1: Final answers under-report maintenance failures.} Several
trajectories can produce plausible summaries while failing the contract. The
failure is visible only through the state assertion, forbidden action, or
missing validation evidence.

\textbf{F2: The useful failure classes are operational.} The most actionable
categories are not generic wrong answers. They are invalid tool calls,
permission violations, unsafe secret access, state-diff errors, routing
errors, parse failures, and missing recovery. Each category points to a
different maintenance response.

\textbf{F3: Repository fixtures make the abstraction inspectable.} The small
fixture is not meant to represent real repository complexity, but it shows what
the contract should eventually scale toward: before/after state, a patch,
validation evidence, and replay metadata.

\section{Implications for Software Evolution}

Agent workflows evolve like software. Prompts change, model versions change,
tool schemas change, repository conventions change, and permission policies
become stricter as agents receive more authority. Without state-diff contracts,
teams cannot distinguish a model regression from a tool-schema bug, stale
memory, overbroad permission, or an underspecified task boundary.

State-diff contracts provide a regression surface for repository-changing
agents. They can be run when a model is upgraded, when a tool schema changes,
when a repository adds a new policy, or when a workflow moves from dry-run to
review-required execution. The result is not just a pass/fail score, but a
failure taxonomy that can guide maintenance.

For software evolution, the important property is comparability over time. If
an agent workflow changes from one model to another, a final-answer comparison
is brittle. A state-diff comparison can ask whether the same expected files
changed, whether the same tests ran, whether the same permission boundaries
were respected, and whether the replay record improved or degraded. This gives
teams a regression surface for agent behavior.

For reengineering, the contract separates durable policy from temporary prompt
scaffolding. A long prompt checklist may be simplified as models improve. A
repository policy, review gate, or secret-access rule should remain explicit.
This distinction helps teams avoid preserving obsolete prompt machinery while
also avoiding the opposite mistake of removing the operational guardrails that
make agent actions auditable.

\section{Threats to Validity}

The pilot uses mock state rather than large production repositories. The case
set is small and hand-designed. The live rows, where used, are descriptive and
should not be generalized to provider quality. The contract language is also
minimal: it demonstrates the analysis surface but does not yet cover complex
multi-repository changes, long-running branches, dependency updates, or
concurrent human review.

An additional threat is that the current fixture encodes a successful
repository change rather than a large corpus of successful and failing patches.
Future work should add realistic repositories, failing tests, partial patches,
merge conflicts, and review comments. The present contribution is therefore a
framing and artifact shape, not a statistical claim about agent reliability.

\section{Conclusion}

Repository-changing agents should be evaluated by what they do to software
state. State-diff contracts make those effects visible, testable, and
replayable. This framing treats an agent run as a software artifact that can be
maintained as models, prompts, tools, and repository policies evolve.
